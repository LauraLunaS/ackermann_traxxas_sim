# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

ROS2 (Jazzy) + Gazebo (Harmonic) simulation of an Ackermann-steered rover (a Traxxas Slash 4x4 VXL Ultimate RC car), built as a test environment for CIn/UFPE's autonomous rover project ("saye"). This is a colcon workspace. Documentation and code comments are primarily in Portuguese.

## Workspace layout

This is a standard colcon workspace:
- `src/ackermann-vehicle-gzsim-ros2/` — the main ROS2 package group (a separate git submodule/subtree-like nested repo, `saye_*` packages):
  - `saye_bringup` — launch files, Nav2/SLAM/bridge config, the waypoint automation script. This is where most simulation-level integration work happens.
  - `saye_description` — Gazebo/SDF robot models, URDF, worlds, meshes. Two robot models exist: `models/traxxas/model.sdf` (the current, Nav2-tuned Traxxas) and the older `models/saye/model.sdf`; plus `models/trailer/` (a towable reboque). Worlds: `worlds/simple_world.sdf` (used by `traxxas_spawn`), `worlds/saye_world.sdf` (used by `saye_spawn`, includes `worlds/media/dune_terrain.obj`), `worlds/warehouse/`.
  - `saye_control` — C++ (rclcpp) nodes: a joystick-based teleop controller and a `ShareMap` service client, built with ament_cmake.
  - `saye_msgs` — custom interfaces: `msg/Map.msg`, `srv/ShareMap.srv`.
- `src/obstacle_avoider/` — a standalone Python ament package (setuptools) with the reactive obstacle-avoidance node and a camera_info publisher.
- `src/saye_tracking/` — 3D multi-object-tracking pipeline (ament_python), kept in this repo (not the nested `saye_*` submodule). Phased build; see its `README.md` for per-phase findings and validation results. Design: tracking-by-detection, motion-only (no ReID), Kalman + association in the **`odom` frame in 3D** (not image plane), OC-SORT-style core. Phases 0–4 (detection → 3D projection via organized point cloud → tracker → motmetrics eval harness + scenario suite) are done and validated; only Phase 5 (dynamic costmap layer) and Phase 6 (better predictor, ByteTrack-style 2-stage association) remain. Model weights (`*.pt`) are gitignored — ultralytics downloads on first run, or drop them in `src/saye_tracking/models/`. Detailed technical log per phase, with validation numbers and lessons learned, is in `.claude/docs/saye_tracking.md`. When stopping a `ros2 launch` from a script, send SIGINT (`send_signal(signal.SIGINT)`) — SIGTERM does not cascade to child nodes.
- `build/`, `install/`, `log/` — colcon output directories. As of commit 833f186 they're `.gitignore`d, but a large set of previously-committed files under them is still tracked; don't hand-edit anything here, it's regenerated by `colcon build`.

## Build

```bash
# From the workspace root
colcon build
source install/setup.bash

# Rebuild a single package (much faster while iterating)
colcon build --packages-select saye_bringup
colcon build --packages-select saye_control

`colcon build` needs user-site `setuptools<80` (colcon-core pins it; setuptools 80+ rejects the `--uninstall`/`--editable` options it passes to `setup.py`). If `ament_python` builds fail with "option --uninstall not recognized", run `pip install --user --break-system-packages "setuptools>=68,<80"`.
```

The `obstacle_avoider` package is a plain pip-installed Python package, not colcon-built in the normal sense — after editing it, reinstall and re-copy its entry points into `install/`:

```bash
cd src/obstacle_avoider
pip install . --break-system-packages
cp ~/.local/bin/obstacle_avoider ~/ackermann_sim/install/obstacle_avoider/lib/obstacle_avoider/obstacle_avoider
cp ~/.local/bin/camera_info_publisher ~/ackermann_sim/install/obstacle_avoider/lib/obstacle_avoider/camera_info_publisher
```

System dependencies (Ubuntu 24.04 / ROS2 Jazzy / Gazebo Harmonic):
```bash
sudo apt install ros-jazzy-ros-gz ros-jazzy-nav2-* ros-jazzy-slam-toolbox ros-jazzy-rtabmap-ros -y
rosdep install --from-paths src --ignore-src -r -y
```

## Tests

`src/obstacle_avoider/test/` has the standard ROS2 ament linter tests (`test_copyright.py`, `test_flake8.py`, `test_pep257.py`), run via colcon:

```bash
colcon test --packages-select obstacle_avoider
colcon test-result --verbose
```

`saye_control` and other `ament_cmake` packages wire up `ament_lint_auto`/`ament_lint_common` under `BUILD_TESTING`; these run as part of `colcon test` after a build.

`src/saye_tracking/test/` is the same ament_python/pytest setup, but each test file is tied to a specific build sub-phase (`test_3_2_ciclo_de_vida.py`, `test_4_3_cenarios.py`, etc.) rather than being general unit tests — check the README's phase table before assuming a given test still reflects current behavior:
```bash
colcon test --packages-select saye_tracking
colcon test-result --verbose
```

## Running the simulation

Each of these needs `source install/setup.bash` first, in its own terminal.

**Basic simulation + reactive obstacle avoidance:**
```bash
ros2 launch saye_bringup traxxas_spawn.launch.py     # Terminal 1: Gazebo + spawn + ros_gz bridge + static TF
python3 -m obstacle_avoider.ackermann_obstacle_avoider  # Terminal 2
```

`traxxas_spawn.launch.py` starts Gazebo (`simple_world.sdf`), spawns the robot, runs the `parameter_bridge`, and — critically — a `static_transform_publisher` linking frame `traxxas` → `traxxas/base_link` (without it `/scan` is not transformable into the Nav2/SLAM base frame and navigation hangs without ever publishing `/cmd_vel`). `robot_state_publisher` and RViz are commented out in this launch file. The older `saye_spawn.launch.py` is the parallel variant for the `saye` model (`saye_world.sdf`, `ros_gz_bridge.yaml`, RSP + RViz on).

**SLAM (build a map):**
```bash
ros2 launch slam_toolbox online_async_launch.py use_sim_time:=true \
  slam_params_file:=$HOME/ackermann_sim/slam_toolbox_params.yaml
# then run the obstacle avoider in another terminal to drive around and explore
# save the map:
ros2 service call /slam_toolbox/save_map slam_toolbox/srv/SaveMap \
  "name: {data: '/home/$USER/ackermann_sim/src/ackermann-vehicle-gzsim-ros2/saye_bringup/maps/map'}"
colcon build --packages-select saye_bringup && source install/setup.bash
```

**Nav2 waypoint navigation:**
```bash
ros2 launch saye_bringup traxxas_spawn.launch.py       # Terminal 1
ros2 launch saye_bringup nav_fisico_sim.launch.py      # Terminal 2 (Nav2 bringup)
rviz2 -d /opt/ros/jazzy/share/nav2_bringup/rviz/nav2_default_view.rviz  # Terminal 3
```
In RViz2: set "2D Pose Estimate" at the robot's actual position, then send "Nav2 Goal".

`nav_fisico_sim.launch.py` includes `nav2_bringup/bringup_launch.py` with `slam:=True`, so it starts `slam_toolbox` itself — don't also launch SLAM separately for this path. Note there are two copies of `slam_toolbox_params.yaml`: the repo-root one (used by the standalone SLAM command above) and `saye_bringup/config/slam_toolbox_params.yaml` (used by `nav_fisico_sim.launch.py`); keep them in sync or know which one is live.

The other Nav2 launch files (`traxxas_navigation.launch.py`, `navigation_bringup.launch.py`) are localization-mode (`slam:=False`) against a saved `maps/map.yaml` with `nav2_params_traxxas.yaml` / `nav2_params.yaml` — currently secondary to `nav_fisico_sim`.

Programmatic waypoint following uses `saye_bringup/scripts/trajectory_waypoints.py` (via `nav2_simple_commander`), reading coordinates from `saye_bringup/config/waypoints.json`. This same script is meant to be copied onto the physical robot's Raspberry Pi for real-world runs — when editing it, keep in mind `caminho_json` is a path that gets manually adjusted per-deployment (sim vs. Pi).

## Architecture notes

**Sim ↔ ROS2 bridge.** Gazebo and ROS2 topics are connected via `ros_gz_bridge parameter_bridge`, configured in `saye_bringup/config/ros_gz_bridge_traxxas.yaml` (the `traxxas_spawn` path; `saye_spawn` uses the older `ros_gz_bridge.yaml`). This is the single source of truth for what sensor/control data crosses the sim boundary: `/cmd_vel` (bidirectional), `/odom` (with `publish_tf: true`), `/scan` (2D lidar), `/tf` (from Gazebo `/model/traxxas/pose`), `/imu`, `/joint_states`, `/camera/front_raw`, `/cloud`, and RealSense-D435-derived `/camera/realsense/{image_raw,depth,points,camera_info}`. Several other cameras (left/right/rear) are present but commented out. When adding a new sensor or topic to the robot model, it must be both declared in `model.sdf` (as a Gazebo sensor/topic) and added here to reach ROS2.

**Robot model and control.** The vehicle kinematics/physics live entirely in `saye_description/models/traxxas/model.sdf` as Gazebo plugins — notably `gz-sim-ackermann-steering-system` (listens on `/cmd_vel`), `gz-sim-odometry-publisher-system` (publishes `odom`), and per-joint `gz-sim-joint-position-controller-system` plugins for an onboard arm (uarm: shoulder_pan/shoulder_lift/elbow/gripper_left/gripper_right). There is no separate ros2_control stack — steering/throttle is driven directly by Gazebo's Ackermann plugin from `Twist` messages on `/cmd_vel`.

**Obstacle avoidance is a standalone reactive FSM**, not part of Nav2. `obstacle_avoider/ackermann_obstacle_avoider.py` implements a 3-state machine (AVANCANDO / DESVIANDO_FRENTE / MANOBRA_RE) purely from `/scan` LaserScan sectors (front/left/right/back), publishing directly to `/cmd_vel`. It runs independently of and is not composed with Nav2 — don't assume Nav2 is active when working on it, and don't assume this node is running during Nav2-based navigation.

**Two independent navigation paths exist and don't share cmd_vel wiring automatically:**
- Reactive: obstacle_avoider → `/cmd_vel` directly.
- Nav2: `nav_fisico_sim.launch.py` includes `nav2_bringup`'s `bringup_launch.py` with `saye_bringup/config/nav2_params_fisico_sim.yaml` and `config/slam_toolbox_params.yaml`. There is **no** `topic_tools relay` in this path (an earlier version had one; it was removed in 833f186). Instead, `nav2_params_fisico_sim.yaml` sets the `collision_monitor`'s `cmd_vel_out_topic: "cmd_vel"`, so the final smoothed + collision-checked command is published straight to `/cmd_vel`. Adding a relay of `/cmd_vel_nav` (raw controller output) here would create two competing publishers — don't. If you add a new velocity-producing node, route it so only one publisher drives `/cmd_vel` at a time.

**saye_control (C++) is a separate, less-integrated control path** — a joystick teleop node and a `ShareMap` service client/server pair (multi-robot map sharing, per `saye_msgs/srv/ShareMap.srv`). It is not wired into the launch files above; it's built and run standalone.

**Config and launch file naming reflects deployment target, not just purpose** — e.g. `nav2_params.yaml` vs `nav2_params_traxxas.yaml` vs `nav2_params_fisico_sim.yaml`, `ros_gz_bridge.yaml` vs `ros_gz_bridge_traxxas.yaml`, and `saye_spawn.launch.py` vs `traxxas_spawn.launch.py`. The `traxxas_*` / `*_fisico_sim` variants are the currently active ones (Traxxas model, Nav2 work); the unsuffixed `saye_*` variants are the older `saye`-model path. Before editing a config, confirm which launch file actually references it (`grep` the filename under `saye_bringup/launch/`) — stale/unused variants exist alongside the active ones.

**Simulated walking people are pre-baked mesh "flipbooks", not Gazebo actors.** Gazebo's `<actor>` (skeletal Collada animation) does not render to any sensor camera on this machine (confirmed with a controlled test — a static box at the same pose renders fine, the actor doesn't), so moving pedestrians use static `<model>` frames instead: `saye_description/models/pessoa_andando_<N>_frame_<k>/` holds one textured pose per native keyframe of the original walk animation (29 for pessoa 1, 27 for pessoa 2), baked by `src/saye_tracking/scripts/bake_walk_frames.py` (linear blend skinning, with skinned normals — without `vn` the textures render white in Gazebo). Each frame's OBJ must reference its own `mtllib walk.mtl` and a unique `usemtl`. The gait follows distance walked: one cycle = animation duration / 4.0 (the `animation_factor` of the reference plugin `blackcoffeerobotics/gazebo-ros-actor-plugin`).

Actors and their paths are defined in `src/saye_tracking/config/atores.yaml` (waypoints in world/odom `(x, y)`, looped; paths may cross — there is no collision). `mover_pessoas_animadas.launch.py` starts one `mover_pessoa_animada_node` per entry, each driving its own flipbook. Pessoa 3 (dark uniform) is baked from the Fuel `mingfei/actor` skeleton (`walk.dae`, one 5.75 s cycle = 1.384 m of travel) with its clothing recolored navy via per-material groups; its cycle is in-place (root motion removed), so `velocidade` must match the native 0.24 m/s to avoid foot sliding. Path math is in `caminhada.posicao_no_caminho`.

**Language convention:** node logic, log messages, and config comments are written in Portuguese (e.g. state names `AVANCANDO`/`DESVIANDO_FRENTE`/`MANOBRA_RE`, variable names like `distancia_segura`). Match this convention when editing existing Portuguese-named code rather than mixing in English identifiers.
